    MikroTik Manager 1.1 (beta)¶

    1.1 is in beta on the dev branch and the :beta images (release channels). For stable, stay on 1.0 below.

    1.1.0-beta.10¶

    Jump hosts say why, in time, from @KevinGinger. With forwarding off on a RouterOS jump router, editing a device to go through it used to end in "Timed out connecting to the device". It now gives RouterOS's reason and the command that fixes it (/ip ssh set forwarding-enabled=local) within the same 10 seconds, and polls, Test and SSH commands do the same within their own time. A device added over SSH only gives the jump host's reason once instead of twice (Jump hosts, #391).

    1.1.0-beta.9¶

    A more readable Capacity & health card, from @azizfayziev's proposal. On the dashboard's Operations tab the card now lists the busiest CPU first, and memory only moves a device up once it reaches 75 %. RouterOS memory use hardly changes, so it used to decide the order on its own. A name prefix shared by every device (01-SITE-) is shown once above the list instead of cutting off every name, and each row shows the model under the name. Loads under 50 % are grey, so the one device running hot stands out. A small graph shows each device's CPU over the last 24 hours, with a dashed line at 75 % and a dot at the day's peak, and a tick on the bar marks that peak too, so a spike can be told from a steady load (#368).

    1.1.0-beta.8¶

    The IPv6 firewall. The Firewall tab has an IPv4 / IPv6 switch. IPv6 has the same address lists, filter rules and NAT as IPv4 (IPv6 NAT needs RouterOS 7), with the same editing, reordering, counters and Review changes. Change Guard can't predict IPv6 lockouts yet, so IPv6 changes run with auto-revert, which is required when the manager connects to the device over IPv6 (Change Guard, #312).

    Also: if Change Guard is set to script mode, an IPv6 firewall change or a VLAN interface change that has to be undone is now reverted on its own, without restoring a backup and rebooting the device.

    1.1.0-beta.7¶

    Add, edit and remove VLAN interfaces. The VLAN interfaces card on a device's VLANs tab used to be read-only. Now it can create a VLAN interface on a port, bond or bridge (with an IP address if you like), change its VLAN ID, parent, name, MTU or comment, disable it, or remove it along with its addresses. Every change runs under Change Guard and can be previewed with Review changes. Changing the VLAN ID or parent of the VLAN interface the manager reaches the device through is now predicted as a lockout, including a VLAN it's stacked on (VLAN interfaces, #309).

    1.1.0-beta.6¶

    Jump hosts, from @KevinGinger: reach devices the manager can't connect to directly through an SSH connection to a router (or any SSH server) that can. Add jump hosts under Credentials, then pick one per device, or as a site's default for new devices. Device API and SSH connections go through it, one shared connection per jump host, with its host key pinned. On a RouterOS jump router, allow forwarding with /ip ssh set forwarding-enabled=local. While devices use a jump host, only a fleet admin can change its address, port or host key (Jump hosts, #375).

    1.1.0-beta.5¶

    The fixes of 1.0.3, for the beta channel: the dashboard no longer warns about missing backups for devices whose configuration hasn't changed, and co-channel overlap is counted per controller and per site. Also routine dependency updates.

    1.1.0-beta.4¶

    The first new features of 1.1, both from @jenserling:

    • 12- or 24-hour time. Times show in 24-hour format by default. Fleet admins set the default for everyone under Settings → General, and each account can choose its own (Time display, #343).
    • Wireless Systems and the antenna aligner. A new device type, shown as WS, for outdoor point-to-point, point-to-multipoint and CPE radios. These devices get an Antenna aligner tab with live signal from one or both ends of a link, per-chain readings, SNR, CCQ, link rates, a signal history and an optional tone. It only reads from the radios and never changes their settings. Existing radios keep their type until you change it in Edit Device (Antenna aligner, #344).

    1.1.0-beta.3¶

    The fixes of 1.0.2, for the beta channel: log collection uses much less CPU (thanks to @KevinGinger, #374), and the backend image no longer copies a checkout's local packages into the build.

    1.1.0-beta.2¶

    The security fixes of 1.0.1, for the beta channel. Update as soon as you can.

    1.1.0-beta.1¶

    No new features yet. This beta upgrades the major libraries underneath the app, so they get tested before the 1.1 features land on top of them: Express 5, BullMQ 6 and ioredis 6, openid-client 6 (SSO), recharts 3, zustand 5 and TypeScript 6. Pages, charts and sign-in should look and work as they did on 1.0. If something doesn't, open an issue and say you're on the beta.

    One thing to check if you use SSO: the Issuer URL has to be the issuer your provider names in its discovery document. A trailing slash either way is fine, but an IP address or a different hostname for the same provider is now refused, and Test discovery gives the URL to use instead (SSO / OIDC). Signing in with the local admin isn't affected.

    MikroTik Manager 1.0¶

    Released on Sunday 1 November 2026, after a week of release candidates (1.0.0-rc.1 to rc.9) tested on real fleets.

    1.0 is the first stable release: a version to run in production, where updates on the 1.0.x line only fix things. It's the result of more than 130 beta releases since April 2026, many of them shaped by people running MikroTik Manager on their own fleets.

    1.0.3¶

    Released on Monday 2 November 2026. Two dashboard warnings that showed when nothing was wrong, both reported by @azizfayziev.

    • "No recent backup" for devices that hadn't changed. A configuration snapshot is only stored when the configuration changes, so a device unchanged for a week was flagged even though its newest backup was current. The hourly check that finds the configuration unchanged now counts as a fresh backup (Backups, #377).
    • "Co-channel overlap" counted radios that don't overlap. It counted a CAPsMAN controller's copies of its CAPs' radios as extra radios, and compared radios across the whole fleet. It now uses the Channel Usage analysis, which compares radios per controller and per site. In Channel Usage, standalone APs are now grouped by site too (Wireless, #365).

    1.0.2¶

    Released on Sunday 1 November 2026.

    • Log collection uses much less CPU. Turning device log times into real times built a new time zone formatter for every line; it now reuses one per zone, which makes a large log poll around 7 to 15 times cheaper. Times come out exactly as before. Thanks to @KevinGinger (#374).
    • Building from a checkout no longer picks up its local packages. The backend image copied the checkout's own node_modules into the build, so a checkout last used on another branch could build a broken image. Only matters if you build the images yourself.

    1.0.1¶

    Released on Sunday 1 November 2026, the same day as 1.0.0. Security fixes, reported by @pimlie; update as soon as you can.

    • Site-scoped accounts could reach other sites' devices (GHSA-j9x4-qwcj-p8v8). An id written in an unusual way ("20" in a list, 0x14, +5, 5x) passed the site check but still reached the device, backup or rollout, so an operator limited to one site could run commands on any device. Ids are now read one way everywhere, a second site check can't raise the role the first one set, and security-check mutes are limited to the account's sites. Installs without site-scoped accounts weren't affected.
    • Device passwords could be sent unencrypted, or to another address (GHSA-63v6-w7qf-349f).
      • Adding a device with no port tried API-SSL and the plain API at the same time, so the password crossed the network unencrypted even when API-SSL worked. The plain API is now tried only when API-SSL isn't available (Devices).
      • Moving a device to another address sent its saved SSH password there. Now only the passwords entered with the move are used (Devices).
      • Alert email didn't check the mail server's certificate. It does now, and requires STARTTLS before sending a login; untick Check the server's certificate on the channel for a server with a self-signed certificate (Alerting).
      • Two-factor codes are limited per account as well as per address, and each code signs in once.
    • RouterBOOT upgrades stayed pending after they were done, and after a RouterOS downgrade an older RouterBOOT was offered as an upgrade (#372).

    Check after updating: if alert email stops arriving, open the channel and use Send test. A mail server with a self-signed certificate, or one that doesn't offer STARTTLS, now needs Check the server's certificate unticked.

    What it does¶

    MikroTik Manager is a self-hosted manager for fleets of MikroTik routers, switches and access points on RouterOS 6 and 7.

    • Inventory and health. Devices grouped into sites and site groups, live status, resources, availability and reboots, hardware sensors, optics and PoE. Adoption of configured and factory-default devices. Devices, Sites, Adopting devices
    • Configuration from one place. Ports, bridges, VLANs (bridge, switch-chip and VLAN interfaces), IPv4 and IPv6 routes with routing tables, firewall and NAT, queues, wireless, DHCP, DNS, NTP, WireGuard, logging, SNMP and LLDP, bulk commands, templates and firmware rollouts in waves.
    • Change Guard. Every change that could cut the manager off is checked against the device's real management path first, and protected by an automatic revert if the device stops answering. Change Guard
    • Security. A posture check for every device (management services, firewall input rules, IPv6, RoMON, certificates), known RouterOS vulnerabilities in the fleet, device certificates from the manager's own CA, SSH keys, and fixes you can apply in one click. Security page
    • Clients, wireless and traffic. Client history and identification, roaming, Wi-Fi radios, RF health, rogue APs, guest Wi-Fi, CAPsMAN, NetFlow traffic analytics, firewall logs, LTE. Clients, Wireless, Traffic analytics
    • Operations. Topology from LLDP and spanning tree, configuration backups and diffs, alerting with webhooks and reports, maintenance windows, platform backup and restore, single sign-on, per-site roles, scoped API tokens and an audit log. Alerting, Backups, API and automation
    • Scale. A poller built for large fleets: batched reads, optional persistent sessions, separate worker processes, and a health view that says when it's falling behind. Polling and scaling

    Upgrading from a beta¶

    No settings need changing. Database migrations run automatically on startup.

    1. Take a platform backup first (Settings → Backup & Restore). It's cheap insurance.
    2. Update as you always have, including the compose file, not only the images (Updating and image versions):
      • from a git checkout: git pull, then docker compose pull && docker compose up -d (or docker compose up -d --build backend nginx if you build locally);
      • with the GHCR compose file: download docker-compose.ghcr.yml again, keep your .env, then pull and start.

    Release channels¶

    From 1.0 there are two channels (details):

    • Stable, the default: main and the :latest images. 1.0.x, fixes only.
    • Beta: dev and the :beta images. New features as betas of the next minor version.

    If you update from main or run :latest today, you're on stable and don't need to do anything. The update notice in the app now understands release candidates and follows your channel.

    Known issues¶

    • On access points using the legacy wireless driver with RouterOS 6, the security of neighbouring networks in AP scans shows as unknown: their scan doesn't report encryption over the API, and RouterOS 6 can't return a script's output the way RouterOS 7 can. On RouterOS 7, MikroTik Manager reads it from the scan run as a script (#295, Wireless).

    After 1.0¶

    Planned for the next minor version, on the beta channel: finer user roles and permissions, editing the IPv6 firewall, adding and editing VLAN interfaces, quick firewall presets, IPsec, PPPoE, EoIP and Netinstall views, resizable client list columns, a read-only MCP connector for AI-assisted reviews, and major dependency upgrades. Issues labelled post-stable are the running list.
